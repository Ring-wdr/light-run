# Google Play 출시 준비

스토어 이름 **라이트런**, 패키지 `com.ringwdr.lightrun`(공유용 변형. README "앱 두 개"), 무료, 광고 없음.
개인 개발자 계정 기준. 2026-10 정책으로 확인했다. 정책은 자주 바뀌니 Play Console 안내가 우선이다.

## 0. 순서 한눈에

1. 서명 키 방식 정하기(§1) — **첫 업로드 전에만 고를 수 있다**
2. 앱 콘텐츠(정책 신고) 채우기(§3), 스토어 등록정보(§4)
3. `production` 프로필로 AAB 빌드 → 비공개 테스트 트랙에 **직접** 업로드(§2)
4. 테스터 12명 이상이 **14일 연속** 참여(§5)
5. 대시보드에서 "프로덕션 액세스 신청" → 승인되면 프로덕션 출시 → 심사

## 1. 서명 키(Play App Signing) — 먼저 정할 것

Play 앱은 Google이 가진 "앱 서명 키"로 서명돼 배포되고, 개발자는 "업로드 키"로 서명해 올린다.
지금 주변에 나눠 준 공유용 APK(EAS `preview`)는 **EAS 키**로 서명돼 있다.

- **Google이 새 키를 만드는 경우(기본값)**: Play에서 받은 앱과 APK의 서명이 달라서 덮어 설치가 안 된다.
  APK 사용자는 기록 › ··· › 전체 기록 백업(GPX) → 앱 삭제 → Play에서 설치 → 백업 불러오기를 해야 한다.
- **EAS 키를 앱 서명 키로 올리는 경우**: 첫 앱 만들기 › 앱 서명에서 "Java 키 저장소에서 기존 앱 서명 키 내보내기 및 업로드"를 고르고
  안내된 PEPK 도구로 EAS 키(`npx eas-cli@latest credentials -p android`에서 키스토어 내려받기)를 암호화해 올린다.
  그러면 Play 버전이 기존 APK 위에 그대로 업데이트된다. 업로드 키는 EAS 키를 그대로 쓰거나 새로 만들어 등록한다.

**결정: Google이 새 키를 만든다(기본값).** 이유
- Expo를 떠나도 묶이지 않는다. 앱 서명 키는 어느 쪽이든 Google이 보관하고, 업로드 키(EAS 키)는 `eas credentials`로 언제든 내려받아 로컬 빌드에 쓸 수 있다.
  업로드 키를 잃어도 Play Console에서 재설정을 요청할 수 있다(앱 서명 키는 잃을 일이 없다).
- 기존 APK 사용자는 지인 몇 명이고, GPX 백업·불러오기로 기록을 옮길 수 있다. PEPK 내보내기 절차와 같은 키를 두 곳에 두는 부담을 질 이유가 적다.
- 대신 출시 뒤에는 EAS `preview` APK와 Play 버전이 서로 덮어 설치되지 않는다. 테스트 빌드는 APK 대신 Play 내부·비공개 테스트 트랙으로 나눠 준다.

어느 쪽이든 EAS 키스토어는 지우지 말 것(이제 업로드 키다). 루트의 `*.jks` 백업은 git에서 제외돼 있다(`.gitignore`).

## 2. 빌드와 업로드

```bash
npx eas-cli@latest build -p android --profile production
```

- `production` 프로필은 AAB(기본값), `APP_VARIANT=production`, `versionCode` 자동 증가(`appVersionSource: remote`).
- 빌드 전 EAS 환경 변수 `production`에 `GOOGLE_MAPS_API_KEY`, `EXPO_PUBLIC_MAPBOX_TOKEN`이 있는지 확인(README "지도 키·토큰").
  Google Cloud Console의 Maps 키 Android 앱 제한에 **Play 앱 서명 키의 SHA-1**을 추가해야 Play에서 받은 앱에 지도가 뜬다
  (Play Console › 테스트 및 출시 › 설정 › 앱 서명에서 복사). 빠뜨리면 지도만 빈 화면이 된다.
- **첫 AAB는 Play Console에 손으로 올린다**(Google API는 첫 업로드를 받지 않는다). 테스트 및 출시 › 비공개 테스트 › 트랙 만들기 › 새 버전.
- 이후부터는 `eas submit`으로 올릴 수 있다. Google Cloud 서비스 계정 JSON 키가 필요하다(EAS가 서버에 보관, 저장소에 넣지 말 것).
  ```bash
  npx eas-cli@latest submit -p android --profile production --latest
  ```
  트랙 지정은 `eas.json`의 `submit.production.android.track`(`internal`, `alpha`=비공개 테스트, `production`).
- 대상 API: 새 앱·업데이트는 **Android 16(API 36) 이상**이어야 한다. Expo SDK 57(RN 0.86)은 `targetSdk 36`이라 맞다.

### 3-1. 데이터 보안 양식

앱 자체는 기록을 기기 밖으로 보내지 않는다(기기 안 처리는 "수집"이 아니다). 다만 지도 SDK가 보내는 정보는 앱이 수집한 것으로 신고해야 한다.
Google Maps SDK 공식 안내: <https://developers.google.com/maps/documentation/android-sdk/play-data-disclosure>.
Mapbox도 같은 성격이다(텔레메트리는 코드에서 껐다, `src/ui/ReplayMap.tsx`). 제출 직전 두 SDK의 최신 안내를 다시 볼 것.

- 데이터를 수집하거나 공유하나요? **예**
- 전송 중 암호화? **예**(HTTPS) · 삭제 요청 방법 제공? **아니요**(개발자가 보관하는 이용자 데이터 없음. 기록은 앱에서 삭제)

| 데이터 유형 | 수집 | 공유 | 목적 | 필수/선택 |
|---|---|---|---|---|
| 앱 정보 및 성능 › 비정상 종료 로그, 진단 | 예 | 아니요(서비스 제공자) | 분석, 앱 기능 | 필수 |
| 기기 또는 기타 ID | 예 | 아니요(서비스 제공자) | 분석 | 필수 |
| 위치 | 아니요(기기 안에서만 처리) | 아니요 | — | — |

### 3-2. 포그라운드 서비스(위치) 신고

정책 › 앱 콘텐츠 › 포그라운드 서비스 권한 › `FOREGROUND_SERVICE_LOCATION`.

- 설명(예시): "사용자가 시작 버튼을 눌러 달리기·걷기 기록을 시작하면 위치 포그라운드 서비스를 켭니다. 화면이 꺼지거나 휴대전화를 주머니에 넣어도
  거리와 경로가 끊기지 않게 하려는 것이며, 기록 중 알림이 계속 표시됩니다. 사용자가 종료를 누르면 서비스를 즉시 멈춥니다."
- 영상(30초 안팎, YouTube 일부 공개 링크): 홈 › 시작 → 위치 권한 "앱 사용 중에만 허용" → 카운트다운 → 기록 화면과 상단 알림 →
  화면 끄기 → 다시 켜서 거리가 늘어난 것 → 종료 → 알림이 사라지는 것.

**백그라운드 위치(`ACCESS_BACKGROUND_LOCATION`)는 쓰지 않는다.** 사용자가 누른 시작으로 켜는 포그라운드 서비스는 "앱 사용 중" 권한으로 충분하다.
권한을 넣으면 위치 권한 신고서·영상 심사 대상이 되고, 포그라운드 서비스로 되는 기능은 거절되기 쉽다. 그래서 Android 매니페스트에서 막았다
(`app.json` `isAndroidBackgroundLocationEnabled: false` + `blockedPermissions`, `src/services/location.ts` 머리 주석).
**실기기 확인 필요**: 이 변경 뒤 화면 끔 30분, 일시정지/재개, 앱 강제 종료 후 복원.

## 5. 비공개 테스트(개인 계정 필수 조건)

2023-11-13 이후 만든 개인 계정은 프로덕션 전에 **비공개 테스트에 12명 이상이 14일 연속 참여**해야 "프로덕션 액세스 신청"이 열린다.
내부 테스트는 세지 않는다. 앱마다 따로 채워야 한다.

- 테스터 목록: 비공개 테스트 트랙 › 테스터 › 이메일 목록(Gmail 계정) 또는 Google 그룹. 15명 이상 넉넉히 모은다(중간에 빠지면 날짜가 다시 셀 수 있다).
- 테스터는 공유 링크에서 **참여(opt-in)** 한 뒤 Play에서 설치해야 한 명으로 센다. 초대만 받고 참여 안 한 사람은 세지 않는다.
- 기존 공유용 APK가 깔린 테스터는 §1 결정에 따라 백업 후 삭제가 필요할 수 있다.
- 14일 동안 실제로 써 보게 하고 피드백을 모은다. 기간 중 업데이트를 1–2번 올리면 신청서의 "테스트 중 무엇을 고쳤나" 질문에 답하기 좋다.
- 신청서 질문: 테스터 모집 방법, 받은 피드백, 앱 대상 사용자, 출시 준비가 된 이유 등. 테스트 중 메모해 둔다.
